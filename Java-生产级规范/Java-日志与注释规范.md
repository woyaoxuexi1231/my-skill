# Java 日志与注释规范

> 范围：只定 **日志怎么打、注释怎么写**。  
> 包结构与分层写法见 `Java-代码架构.md`、`Java-模块代码规范.md`。  
> 注释与日志是交付物的一部分，不是收尾可选项。

---

## 1. 总原则

|     | 日志           | 注释            |
| --- | ------------ | ------------- |
| 目的  | 线上/联调能排障     | 后人懂**为什么**这样写 |
| 优先  | 关键上下文 + 正确级别 | 解释决策、规则、权衡    |
| 避免  | 刷屏、泄密、无信息    | 复述代码「做了什么」    |

目标：另一位开发者（或未来的你）能定位故障，并理解重要决策为何如此。

## 2. 日志

### 2.0 实现选型

- **新项目**：用 Spring Boot 默认的 **Logback**（`spring-boot-starter-logging`），业务代码只打 **SLF4J**。不要再额外引入 Log4j2 / `spring-boot-starter-log4j2`，没必要。
- **已有项目**：已经是 Log4j2（或其它已跑通的实现）→ **不必纠结、不必为换而换**；继续用即可，写法仍走 SLF4J。
- 禁止同一工程混用两套实现抢桥接（易丢日志或重复打印）。

### 2.1 必须

- 只用 **SLF4J 门面**（`LoggerFactory.getLogger`），禁止业务代码直接依赖 Logback / Log4j2 等实现方 API。
- 异常与业务失败：带上**足够上下文**（关键业务 id、操作、失败原因）+ **异常堆栈**（保留 cause / 传 `Throwable`）。
- 级别用对：`ERROR` 系统/逻辑出错；`WARN` 可恢复异常、用户参数问题、降级；`INFO` 关键业务节点；`DEBUG` 细节排查。生产默认关 DEBUG。
- `trace`/`debug`/`info`：**必须用占位符**（或先 `isDebugEnabled`），禁止 `+` 拼接后再判断级别（白做 toString）。
- 同一项目日志风格一致；扩展日志文件名建议：`appName_logType_logName.log`（如 `order_monitor_timeout.log`）。
- Logger 配置避免重复打印：相关 logger 设 `additivity=false`。

### 2.2 禁止

- 记录：密码、Access Token、Authorization 头、密钥/私钥、不必要的敏感个人信息。
- 默认给每个方法打进入/退出日志。
- `catch (Exception e) { log.error("error", e); }` 当万能处理且不再上抛/映射。
- 用日志代替返回值或控制流（「打了日志就算处理完」）。
- 无意义刷屏把磁盘打满；上线临时观察日志用完要删或降级。
- 新项目为「看起来更强」而改 Log4j2 或同时引入两套日志实现。

### 2.3 推荐形态

```text
好：占位符 + 业务键 + 动作 + 结果/原因 + 异常对象
log.warn("创建订单失败 orderId={} userId={} reason={}", orderId, userId, e.toString(), e);

差：无上下文 / 字符串拼接
log.error("error", e);
log.debug("id=" + id + ", obj=" + obj);  // 即使最终不打印也会拼接
log.info("start"); log.info("end");
```

外部 IO（HTTP/RPC/Redis）失败：记清对端标识、超时/状态码等（仍不记密钥与完整敏感载荷）。

## 3. 注释

### 3.1 原则：写「为什么」

优先回答：

```text
为什么这样设计？
为什么用这个算法 / 这条 SQL？
为什么是这个事务边界？
为什么有这个变通？何时可删？
为什么要同步 / 缓存 / 这笔校验？
```

少写：

```text
获取用户
循环订单
调用 xxx 方法
```

### 3.2 必须增加信息

差：

```java
// Get user
User user = userService.getById(id);
```

好：

```java
// 分页必须在数据库完成：订单量会持续增长，不能先全量加载再在内存分页。
```

好：

```java
// 同一事务覆盖扣库存与创建订单：任一步失败两侧都不应提交，二者是同一业务操作。
```

### 3.3 该写注释的类别（出现时就要写）

| 类别        | 写什么                                 |
| --------- | ----------------------------------- |
| 业务规则      | 非显而易见的约束与分支原因                       |
| 技术决策      | 为何选 Redis / 为何不用某 API               |
| 性能        | 为何只查部分列、为何避免 N+1                    |
| 数据库 / SQL | 为何 JOIN 如此组织、条件在 ON 还是 WHERE、索引友好写法 |
| 安全        | 为何不直接暴露 Entity、为何脱敏                 |
| 兼容 / 变通   | 为何存在、何时可删                           |
| 并发        | 锁范围与要防的竞态                           |

### 3.4 密度

```text
类        → 职责不明显、边界/约束非显而易见时写清
方法      → 公共 API、重要用例、复杂行为：目的、关键参数/返回、异常、副作用
复杂逻辑  → 解释为什么
重要决策  → 解释权衡
变通方案  → 为何存在、何时可删
```

不需要：简单 getter/setter、显而易见的赋值、琐碎委托、复述方法名的空 Javadoc（如 `/** 用户服务 */`）。

### 3.5 类 / 方法注释

- 类、类属性、类方法的说明优先 **Javadoc**（`/** ... */`），不要用 `//` 顶替对外 API 文档。
- 所有对外公开方法（含接口方法）要有 Javadoc：做什么、关键参数/返回、异常；枚举字段说明用途。
- 类上建议标明作者与创建日期（团队若有统一模板则从其规范）。
- 单行注释 `//` 与内容之间一个空格；注释与代码同步修改，过时注释必须删改。

重要类说明：职责、边界、非显而易见约束。

```java
/**
 * 订单创建与生命周期流转。
 * <p>创建用例的事务边界在本类：订单落库与扣库存必须同成同败。</p>
 */
```

公共 API / 重要 Service 方法：写目的与副作用，不要只重复方法名。

```java
/**
 * 创建订单并在同一事务内预留库存。
 * <p>库存不足时不持久化订单。</p>
 */
```

### 3.6 SQL 注释

复杂 SQL 注释「为何」：JOIN 组织、条件位置、看似多余的条件、分页策略。  
不要注释显而易见的 SQL 语法本身。

### 3.7 注释必须正确

```text
代码已改 → 审查相关注释 → 更新或删除过时注释
```

错误注释比没有注释更糟。  
不要用注释弥补烂命名：先改名（如 `calculateAvailableInventory()`），再补真正需要的「为什么」。

### 3.8 与分层的衔接

- Controller 每个接口：至少一句说明「干什么」（用途）。
- Service 重要用例 / 事务边界 / 非显而易见规则：按上面类别补注释。
- Mapper XML 复杂语句：补 SQL「为什么」。

## 4. Emoji（允许，克制）

日志和注释**可以适当**使用 emoji：提升阅读体验，并提高日志扫读时的**区分度**。

### 4.1 原则

- **适当、少量、有辨识度**——不是装饰义务。
- **禁止**每条注释、每条日志都加；禁止一串表情刷屏。
- 同一类事件尽量固定同一emoji，形成扫读习惯（例如失败用同一类符号）。

### 4.2 适合加的地方

| 场景 | 说明 |
|------|------|
| 关键路径节点 | 启动完成、定时任务开始/结束、重要业务里程碑 |
| 失败 / 降级 / 告警 | 让 ERROR/WARN 在控制台更容易被扫到 |
| 注释里的警告性说明 | 如并发陷阱、不可删的变通、安全注意 |
| 分区感强的模块日志前缀 | 少数几个稳定符号区分子系统（可选） |

### 4.3 不适合加的地方

- 每行业务注释、每个 getter、每条 DEBUG 细节。
- 对外 API 文档若需机器解析且约定纯文本时，不要依赖 emoji 表达语义。
- 用 emoji 代替清楚的文字（表情不能替代 `orderId=` 等上下文）。

### 4.4 示例

```java
// ⚠️ 锁仅覆盖库存行更新，防止并发超卖；勿扩大到外部 HTTP。
log.info("✅ 订单已创建 orderId={}", orderId);
log.error("❌ 扣库存失败 orderId={} skuId={}", orderId, skuId, e);
```

不必强行统一成某一套表情表；项目内保持克制与大致一致即可。

## 5. 核对清单

**日志**

- [ ] 新项目用 Boot 默认 Logback；未多余引入 Log4j2；业务只打 SLF4J  
- [ ] 失败日志有业务上下文、堆栈与正确级别  
- [ ] debug/info 用占位符，无无效字符串拼接  
- [ ] 无密码/Token/密钥/多余敏感信息  
- [ ] 无方法进出刷屏；无「只打日志不处理」；无重复打印  
- [ ] emoji（若有）只出现在关键/失败等合理点，未滥用  

**注释**

- [ ] 重要决策/规则/SQL/事务有「为什么」  
- [ ] 无复述代码的废话注释；无与代码矛盾的注释  
- [ ] 公共 API / 重要类方法注释有信息量  
- [ ] Controller 接口有用途说明  
- [ ] emoji（若有）用于警示或分区，未每条都加  

打回示例：「这条注释只是复述代码，改成写为什么。」 / 「失败日志缺 orderId。」 / 「emoji 过密，只保留关键节点。」
