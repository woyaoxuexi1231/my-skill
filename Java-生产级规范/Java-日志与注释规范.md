# Java 日志与注释规范

> 范围：只定 **日志怎么打、注释怎么写**。  
> 注释与日志是交付物的一部分，不是收尾可选项。

---

## 0. 三条硬底线

| # | 底线 | 说明 |
|---|------|------|
| 1 | **禁止一行流 Javadoc** | `/** 按 token 恢复会话，返回当前用户资料。 */` 只是把方法名翻译成中文，等于没写。 |
| 2 | **方法体内必须有步骤注释** | 只有方法注释、方法体里一坨裸代码 = 读者只知道「这方法干嘛」，不知道「里面怎么干」。 |
| 3 | **类/方法注释用富文本** | Javadoc 支持段落、列表、`@param`/`@return`/`@throws`，不要用一行话糊过去。 |

**最常见的失败形态：** 方法注释一行流，方法体 50 行零注释。

```java
// ❌ 典型失败样本：注释复述方法名，方法体全程裸奔
/** 按 token 恢复会话，返回当前用户资料。 */
public UserProfile restoreSession(String token) {
    SessionClaims claims = tokenCodec.decode(token);
    Session session = sessionStore.find(claims.sessionId());
    if (session == null) {
        throw new BizException(ErrorCode.SESSION_EXPIRED);
    }
    sessionStore.extendTtl(session.id(), TTL);
    return profileAssembler.toSnapshot(session.userId());
}
```

## 1. 注释的三层结构

一段完整的注释由三层构成，各回答不同问题，**缺一层就不完整**：

| 层级 | 位置 | 回答什么 | 形态 |
|------|------|----------|------|
| 类注释 | 类声明上方 | 这个类的职责边界、非显而易见约束 | 富文本 Javadoc |
| 方法注释 | 方法声明上方 | 做什么、入参/返回/异常/副作用 | 富文本 Javadoc |
| **行间注释** | 方法体内 | **这段代码分几步、每步干什么、为什么** | **步骤式 + emoji** |

三层的读者视角：

```text
类注释   → 我要不要改这个类？它管什么、不管什么
方法注释 → 我要不要调这个方法？传什么、返回什么、会抛什么
行间注释 → 我要改这段逻辑，它分几步、哪一步有坑
```

## 2. 类注释（富文本）

### 必须

- 每个非 trivial 类都要有类注释，写清**职责边界**与**约束**。
- 用富文本：`<p>` 分段，`<ul>/<li>` 列条目，`<p><b>注意：</b></p>` 标约束。
- 约束要具体：事务边界在哪、线程安全与否、不可变的假设、不能往里塞什么。

### 反例 vs 正例

```java
// ❌ 一行流，等于把类名翻译一遍
/** 订单服务。 */
public class OrderService { }
```

```java
// ✅ 富文本：边界 + 约束 + 不属于这里的
/**
 * 订单创建与生命周期流转。
 *
 * <p>职责：创建订单、取消订单、查询订单详情。订单支付与退款不在此类。</p>
 *
 * <p><b>事务边界：</b>创建用例的事务在本类方法上，订单落库与扣库存必须同成同败；
 * 方法内不做远程调用，避免长事务占用连接。</p>
 *
 * <p><b>约束：</b>本类不直接感知 HTTP 层，出入参一律用本模块 DTO，不外泄 Entity。</p>
 */
public class OrderService { }
```

### 常用富文本标签

| 标签 | 用途 |
|------|------|
| `<p>…</p>` | 一个段落；多段用多个 `<p>` |
| `<ul><li>…</li></ul>` | 并列条目（职责清单、注意事项） |
| `<b>…</b>` / `<code>…</code>` | 强调 / 代码元素 |
| `@author` | 可选；团队有约定才加 |

## 3. 方法注释（富文本）

### 3.1 必须包含什么

| 要素 | 何时必写 |
|------|----------|
| 一句目的 | **总是** |
| 补充段落（边界、失败行为、副作用） | 有非显而易见行为时**必须**写 |
| `@param` | 参数含义不自明、有单位/格式/取值范围要求时 |
| `@return` | 返回值语义不自明、可能为空、是快照还是实时值时 |
| `@throws` | 抛业务异常时写清**什么条件下抛、抛哪个错误码** |
| `@implNote` / 注意段 | 有性能、并发、兼容方面的隐含约定时 |

**判断标准：把方法名和签名遮住，只看注释，能否知道该不该调、怎么调、会出什么事。** 不能 → 重写。

### 3.2 反例 vs 正例

```java
// ❌ 一行流：把方法名翻译成中文，没有任何新增信息
/** 按 token 恢复会话，返回当前用户资料。 */
public UserProfile restoreSession(String token) { }
```

```java
// ✅ 富文本：目的 + 失败行为 + 参数/返回/异常
/**
 * 按 token 恢复会话并返回当前用户资料。
 *
 * <p>用于客户端重启或页面刷新后重建登录态：token 有效则顺带续期并返回资料，
 * 失效或已过期则抛业务异常交给上层跳登录——<b>不返回 null</b>，调用方无需判空。</p>
 *
 * <p>资料为调用时刻的快照，不随后续资料变更自动刷新。</p>
 *
 * @param token 登录态令牌，来自客户端本地存储，允许为空串（按无效处理）
 * @return 当前登录用户的资料快照
 * @throws BizException {@code SESSION_EXPIRED} 令牌失效、过期或已被踢下线
 */
public UserProfile restoreSession(String token) { }
```

新增的信息有五处：使用场景、续期副作用、不返回 null、快照语义、失效条件。翻译方法名只能得到零处。

### 3.3 不需要写的情况

- 简单 getter/setter、显而易见的委托。
- 方法名已完整表意、且没有非显而易见行为时，可只写一句目的，**不必凑字数**。
- 但「有内容可写却偷懒写一行」按 §0 第 1 条打回。

## 4. 行间注释（分步骤）——重点

**这是最容易被省略、也最影响可读性的一层。**

方法注释说明「做什么」，行间注释说明「怎么做的、分几步、每步为什么」。缺了它，读代码的人只能逐行反推意图。

### 4.1 硬性要求

| 触发条件 | 要求 |
|----------|------|
| 方法体非空行 **≥ 10 行** | 必须有步骤注释 |
| 方法体含 **≥ 3 个逻辑段落**（空行分隔的代码块） | 每段至少一行注释 |
| 有 `if` / `switch` / `try-catch` / 循环，且其中做了非显而易见的事 | 必须注释**为什么**走这个分支 |
| 有校验、转换、过滤、聚合等多步处理 | 按步骤编号注释 |

### 4.2 写法：编号步骤

用 **`n️⃣` 数字序号**开头，一眼看出这是第几步、一共几步：

```java
// 1️⃣ 干什么
// 2️⃣ 干什么
// 3️⃣ 干什么
```

每步写两段信息，**先说干什么，必要时补为什么**：

```java
// 2️⃣ 查会话：Redis 里没有说明已过期或被踢，按未登录处理
```

### 4.3 步骤数量

**控制在 3~7 步。** 超过 7 步说明这个方法承担了太多事情——先考虑拆方法，而不是写第 8 步注释。

### 4.4 emoji 用法

| 场景 | 符号 | 说明 |
|------|------|------|
| 步骤序号 | 1️⃣ 2️⃣ 3️⃣ | 默认用法，让步骤可扫读 |
| 警告 / 坑 | ⚠️ | 并发陷阱、不可删的变通、易踩的坑 |
| 外部依赖 / IO | 🌐 | 跨服务调用、第三方接口（可选） |
| 性能相关 | ⚡ | 这里做了优化或有性能约束（可选） |

原则：**步骤序号用 emoji 是常态，装饰性 emoji 是例外。** 不要每行都加，不要一串表情刷屏。

### 4.5 完整示例

把 §0 的失败样本改写成合格版本：

```java
/**
 * 按 token 恢复会话并返回当前用户资料。
 *
 * <p>用于客户端重启或页面刷新后重建登录态：token 有效则顺带续期并返回资料，
 * 失效或已过期则抛业务异常交给上层跳登录——<b>不返回 null</b>。</p>
 *
 * @param token 登录态令牌，允许为空串（按无效处理）
 * @return 当前登录用户的资料快照
 * @throws BizException {@code SESSION_EXPIRED} 令牌失效、过期或已被踢下线
 */
public UserProfile restoreSession(String token) {
    // 1️⃣ 解析并校验签名：失败直接抛，不让无效态继续往下走
    SessionClaims claims = tokenCodec.decode(token);

    // 2️⃣ 查会话：Redis 中不存在即视为过期或被踢，不区分两种原因
    Session session = sessionStore.find(claims.sessionId());
    if (session == null) {
        throw new BizException(ErrorCode.SESSION_EXPIRED);
    }

    // 3️⃣ 滑动续期：每次访问顺带延长 TTL，避免活跃用户被登出
    sessionStore.extendTtl(session.id(), TTL);

    // 4️⃣ 组装资料快照：只查这一屏需要的字段，不整表捞
    return profileAssembler.toSnapshot(session.userId());
}
```

再看一个含分支与坑的例子：

```java
public void cancelOrder(Long orderId, String operator) {
    // 1️⃣ 加行锁查询：并发重复取消时，后到的请求会在这里等到前一个事务结束
    Order order = orderMapper.selectForUpdate(orderId);

    // 2️⃣ 幂等判断：已取消直接返回，避免重复退库存
    if (OrderStatus.CANCELED == order.getStatus()) {
        log.info("订单已取消，跳过 orderId={}", orderId);
        return;
    }

    // 3️⃣ 校验可取消状态：已发货的订单必须走售后流程，不能直接取消
    if (!order.getStatus().canCancel()) {
        throw new BizException(ErrorCode.ORDER_CANNOT_CANCEL);
    }

    // 4️⃣ 同一事务内更新状态并退库存：两步必须同成同败
    orderMapper.updateStatus(orderId, OrderStatus.CANCELED);
    inventoryService.release(order.getSkuId(), order.getQuantity());

    // ⚠️ 5️⃣ 通知放在事务提交后：失败只影响通知，不能回滚已完成的取消
    eventPublisher.publish(new OrderCanceledEvent(orderId, operator));
}
```

### 4.6 行间注释反模式

```java
// ❌ 逐行复述代码（等于把 Java 翻译成中文）
User user = userMapper.selectById(id);      // 根据 id 查询用户
user.setName(request.getName());            // 设置名称
userMapper.updateById(user);                // 更新用户

// ❌ 只有方法注释，方法体裸奔
// ❌ 注释与代码矛盾（改了代码没改注释）
// ❌ 用注释解释烂命名（应改名，见 §10）
// ❌ 每步都加装饰 emoji，看不出重点
```

**判断一句行间注释是否有价值：删掉它，读者会不会多花时间才能看懂？** 不会 → 删掉这句注释。

## 5. 注释内容：写「为什么」

编号步骤里的「为什么」部分，优先回答这些：

```text
为什么这样设计？为什么用这个算法 / 这条 SQL？
为什么是这个事务边界？为什么要同步 / 缓存 / 这笔校验？
为什么有这个变通？何时可删？
这个分支防的是什么情况？
```

不写：

```text
获取用户 / 循环订单 / 调用 xxx 方法 / 设置名称
```

## 6. 该写注释的类别（出现时就要写）

| 类别 | 写什么 |
|------|--------|
| 业务规则 | 非显而易见的约束与分支原因 |
| 技术决策 | 为何选 Redis / 为何不用某 API |
| 性能 | 为何只查部分列、为何避免 N+1 |
| 数据库 / SQL | 为何 JOIN 如此组织、条件在 ON 还是 WHERE、索引友好写法 |
| 安全 | 为何不直接暴露 Entity、为何脱敏 |
| 兼容 / 变通 | 为何存在、何时可删 |
| 并发 | 锁范围与要防的竞态 |
| 边界值 | 为什么是这个阈值、超时、数量上限 |

## 7. 各层注释要点

| 层 | 要求 |
|----|------|
| Controller | 每个接口方法注释写用途；类注释写这一组接口的归属资源 |
| Service | 类注释写职责边界与事务边界；方法注释写用例、失败行为；方法体必须有步骤注释 |
| Mapper | 接口方法注释写查询语义与返回形态；XML 复杂语句写 SQL「为什么」（见 §8） |
| Entity / DTO | 字段含义不自明时加注释；枚举每个值写清业务含义 |
| config / 装配类 | 写清这个 Bean 解决什么问题、为什么这样配 |

## 8. SQL 注释

复杂 SQL 注释「为何」：JOIN 组织、条件在 `ON` 还是 `WHERE`、看似多余的条件、分页策略、索引友好写法。

```sql
-- 用 LEFT JOIN 保留无订单用户：统计口径要求分母是全部活跃用户
-- 状态条件放在 ON 而非 WHERE，否则 LEFT JOIN 会退化成 INNER JOIN
SELECT u.id, COUNT(o.id) AS order_count
FROM user u
LEFT JOIN orders o ON o.user_id = u.id AND o.status = 'PAID'
WHERE u.is_deleted = 0
GROUP BY u.id;
```

不要注释显而易见的 SQL 语法本身。

## 9. Emoji（允许，克制）

### 原则

- **适当、少量、有辨识度**——不是装饰义务。
- 步骤序号 emoji 属于**结构化用法**，不在此限（见 §4.4）。
- **禁止**每条注释、每条日志都加；禁止一串表情刷屏。
- 同一类事件固定同一 emoji，形成扫读习惯。

### 适合加的地方

| 场景 | 说明 |
|------|------|
| 行间步骤序号 | 1️⃣ 2️⃣ 3️⃣（默认用法） |
| 警告性说明 | 并发陷阱、不可删的变通、安全注意（⚠️） |
| 失败 / 降级 / 告警日志 | 让 ERROR/WARN 在控制台更容易被扫到 |
| 关键路径节点 | 启动完成、定时任务开始/结束、重要业务里程碑 |

### 不适合加的地方

- 每行业务注释、每个 getter、每条 DEBUG 细节。
- 需机器解析的对外 API 文档（不要依赖 emoji 表达语义）。
- 用 emoji 代替清楚的文字（表情不能替代 `orderId=` 等上下文）。

### 示例

```java
// ⚠️ 锁仅覆盖库存行更新，防止并发超卖；勿扩大到外部 HTTP。
log.info("✅ 订单已创建 orderId={}", orderId);
log.error("❌ 扣库存失败 orderId={} skuId={}", orderId, skuId, e);
```

## 10. 注释必须正确

```text
代码已改 → 审查相关注释 → 更新或删除过时注释
```

- 错误注释比没有注释更糟。
- **不要用注释弥补烂命名**：先改名（如 `calculateAvailableInventory()`），再补真正需要的「为什么」。
- 代码重构后，步骤编号要重新连续（不要出现 1️⃣ 2️⃣ 5️⃣）。

## 11. 日志

### 11.1 必须

- 异常与业务失败：带上**足够上下文**（关键业务 id、操作、失败原因）；需要时带上异常对象（保留 stack）。
- 级别用对：`ERROR` 需处理的失败；`WARN` 可恢复异常/降级；`INFO` 关键业务节点；`DEBUG` 细节排查。
- 同一项目日志风格一致（文案结构、是否带业务前缀等）。

### 11.2 禁止

- 记录：密码、Access Token、Authorization 头、密钥/私钥、不必要的敏感个人信息。
- 默认给每个方法打进入/退出日志。
- `catch (Exception e) { log.error("error", e); }` 当万能处理且不再上抛/映射。
- 用日志代替返回值或控制流（「打了日志就算处理完」）。

### 11.3 推荐形态

```text
好：带业务键 + 动作 + 结果/原因
log.warn("创建订单失败 orderId={} userId={} reason={}", orderId, userId, e.toString(), e);

差：无上下文
log.error("error", e);
log.info("start"); log.info("end");
```

外部 IO（HTTP/RPC/Redis）失败：记清对端标识、超时/状态码等（仍不记密钥与完整敏感载荷）。

### 11.4 与步骤注释的配合

方法体内**先有步骤注释说明意图**，关键失败点再打日志——注释给读者，日志给线上：

```java
// 3️⃣ 调支付网关：超时按未决处理，不重复发起扣款
try {
    PayResult result = payClient.charge(request);
} catch (TimeoutException e) {
    // ⚠️ 未决订单留给对账任务兜底，此处只告警
    log.error("❌ 支付网关超时 orderId={} amount={}", orderId, amount, e);
    throw new BizException(ErrorCode.PAY_PENDING);
}
```

## 12. 核对清单

**注释**

- [ ] 无一行流 Javadoc；类/方法注释用富文本（`<p>` / `<ul>` / `@param` / `@return` / `@throws`）  
- [ ] 类注释写清职责边界与约束  
- [ ] 方法注释能独立回答「该不该调、怎么调、会出什么事」  
- [ ] **方法体 ≥10 行或有多个逻辑段落的，有编号步骤注释（1️⃣ 2️⃣ 3️⃣）**  
- [ ] 步骤数 ≤ 7；超过说明方法该拆  
- [ ] 分支/循环/异常处理写了「为什么走这个分支」  
- [ ] 重要决策/规则/SQL/事务/并发有「为什么」  
- [ ] 无复述代码的废话注释；无与代码矛盾的注释  
- [ ] 复杂 SQL 有「为什么」注释  
- [ ] emoji 用于步骤序号与警示，未滥用  

**日志**

- [ ] 失败日志有业务上下文与正确级别  
- [ ] 无密码/Token/密钥/多余敏感信息  
- [ ] 无方法进出刷屏；无「只打日志不处理」  
- [ ] emoji（若有）只出现在关键/失败等合理点，未滥用

**打回语**

- 「这是把方法名翻译了一遍，重写：写清失败行为、副作用、异常条件。」  
- 「方法体 40 行零注释，补编号步骤注释。」  
- 「步骤注释只写了『查询用户』，没说为什么这么查。」  
- 「第 3 步删了，编号还是 1️⃣2️⃣4️⃣，重排。」  
- 「失败日志缺 orderId。」  
- 「这条注释与代码矛盾，更新后再提。」  
- 「8 步了，先拆方法再补注释。」  
- 「emoji 过密，只在步骤序号和警示处保留。」
