# Java 外部调用规范

> 范围：Redis、HTTP/RPC、消息中间件及其他进程外依赖的**写法与约定**。  
> 业务何时必须用缓存/MQ 由需求决定；本篇管：一旦用了，代码怎么写才算规范。  
> 装配类放 `config/`；调用多在 Service 或明确的客户端组件（见 `Java-代码架构.md`）。

---

## 1. 总则

每个外部依赖在代码里都要能回答：

```text
超时多少？失败怎么办？要不要重试？是否幂等？
关键资源（连接池/线程）有界吗？
```

| 必须 | 禁止 |
|------|------|
| 超时、失败语义写清楚（代码或配置） | 无限重试；失败吞掉当成功 |
| 长耗时外部调用默认放在 DB 事务外 | 无理由把 HTTP/MQ 塞进大事务 |
| 客户端/模板集中配置，业务侧注入使用 | 业务方法里随手 `new` 无超时的客户端 |
| 日志带对端标识与失败原因（不泄密） | 把 Token、密钥、完整敏感载荷打进日志 |

```text
连贯 DB 写 → 事务内
HTTP / MQ / 不确定耗时的 IO → 默认事务外；想清楚补偿与幂等
```

## 2. HTTP / RPC

### 必须

- 连接超时、读超时（及项目约定的总超时）可配置。
- 对可重试错误与不可重试错误区分处理；重试必须有上限与退避，禁止死循环重试。
- 需要幂等的写操作：用幂等键或业务唯一约束，避免重试造成重复下单/重复扣减。
- 状态码与业务错误映射到统一异常/错误模型，不把对方堆栈原文甩给前端。

### 禁止

- 无超时的默认客户端直接打生产。
- 在 Stream/`for` 里打出大量无界外部请求（易打爆对端与自身线程）。
- 把外部响应 `Map` 直接当对外 API 契约往上抛（应收敛成明确类型）。

## 3. Redis

### 使用前提（编码纪律）

不要因为「Redis 很快」就加。代码合入前能说清：缓存/计数/会话/锁等**当前用途**。无用途则不要引入。

### 必须明确

| 项 | 说明 |
|----|------|
| Key 结构 | 可预测、可排查；避免无命名空间的随意字符串 |
| TTL | 有过期策略的数据必须设 TTL（除非有意永久且有说明） |
| 序列化 | 项目内一致；升级兼容要想清楚 |
| 失败行为 | Redis 宕了是降级、失败、还是读库？写进代码路径，禁止静默当命中 |
| 与 DB 一致性 | 更新后如何失效/更新缓存；禁止长期返回错误旧数据还当真相 |

### 禁止

- 无 TTL 的脏缓存越堆越大却无人负责。
- 缓存穿透/击穿无任何防护时，对热点路径粗暴全打到 DB 又无说明（至少要有意识处理或限流）。
- 把大业务对象无分页地塞进单个 key 当「图省事」。

## 4. 消息中间件（MQ 等）

### 必须

- 生产者：发送失败可感知；需要可靠投递时按项目选型使用确认/事务消息等机制，并写清语义。
- 消费者：默认按**至少一次**考虑 → 业务处理要幂等；失败进重试/死信策略明确，禁止无限毒丸循环。
- 消息体用明确类型或约定 schema；关键字段可版本化时不要 silently 改义。

### 禁止

- 未用到 MQ 就先引入依赖与空消费者「占坑」。
- 消费者里吞掉异常导致消息「假成功」丢失。
- 在消费者里开超长 DB 事务又调外部 HTTP 无边界。

---

## 5. 其他外部依赖（OSS、短信、邮件、第三方 SDK…）

同样适用 §1：超时、失败、重试上限、密钥走配置、日志不泄密。  
封装成明确组件（如 `SmsClient`），不要在各个 Service 里复制粘贴 SDK 样板。

---

## 6. 核对清单

- [ ] 凡外部调用均有超时与失败路径  
- [ ] 无无限重试；写路径考虑幂等  
- [ ] 外部 IO 默认不在 DB 事务内  
- [ ] Redis：Key/TTL/失败与失效策略清楚  
- [ ] MQ：消费幂等与死信/重试清楚  
- [ ] 未引入用不到的中间件
