# MySQL 数据库规范

> 范围：**数据库本身**——库表设计、字段类型、索引、SQL 写法、实例参数与运维。  
> 来源要点对齐《阿里巴巴 Java 开发手册》MySQL 章，并按本仓库写法收敛为可执行条文。  
> 不管：应用侧 ORM 框架怎么用、事务怎么标注、代码怎么组织。

---

## 1. 建表规约

### 必须

| 规则 | 说明 |
|------|------|
| 是否字段 `is_xxx`，类型 `unsigned tinyint`（1 是 / 0 否） | 如逻辑删除 `is_deleted`；非负数字段用 unsigned |
| 库名/表名/字段名：小写字母或数字 | 禁大写；禁数字开头；禁两个下划线中间只出现数字（如 `level_3_name`） |
| 表名用单数 | 表示实体，不表示数量 |
| 禁用保留字 | 如 `desc`、`range`、`match`、`delayed` 等 |
| 索引命名 | 主键 `pk_字段名`；唯一 `uk_字段名`；普通 `idx_字段名` |
| 小数用 `decimal` | 禁 `float` / `double`（精度损失） |
| 长度几乎固定的串用 `char` | — |
| `varchar` 不超过 5000 | 更长用 `text` 并**独立表** + 主键关联，避免拖累其它字段索引 |
| 表必备三字段 | `id`（主键，推荐 `unsigned bigint`，单表自增步长 1）、`gmt_create`、`gmt_modified`（`datetime`；也可用项目统一的 `create_time`/`update_time`，但必须有创建与修改时间） |

### 推荐

- 表名：`业务_作用`，如 `trade_order`、`pay_refund`。
- 库名与应用名尽量一致。
- 改字段含义或状态枚举时，**同步更新字段注释**。
- 适当冗余提升查询：仅冗余少改、非超长字段；并保证一致性策略说得清。
- 单表行数超约 **500 万** 或容量超约 **2GB** 再考虑分库分表；预估三年到不了就不要过早拆。
- 字符长度按真实范围选型（能 `tinyint` 不用 `int`），节约空间与索引。

## 2. 索引规约

### 必须

- 业务上具备唯一性的字段（含组合）→ **建唯一索引**（勿只靠应用层「先查后插」）。
- **超过 3 张表禁止 join**；join 字段类型必须一致，关联列要有索引。
- `varchar` 建索引必须指定**长度**（按区分度，不必全长）；可用  
  `count(distinct left(列, 长度))/count(*)` 评估。
- 页面搜索：**禁止**左模糊 / 全模糊（`%xx` / `%xx%`）；需要则走搜索引擎。

### 推荐

- `order by` 尽量利用组合索引有序性：等值条件列在前，排序列在索引最右；范围条件会破坏后续有序性。
- 能覆盖索引就覆盖，减少回表（`explain` 中 `Using index`）。
- 深分页：控制页深，或延迟关联（先查 id 再回表），勿大 offset 硬翻。
- `explain` 目标：至少 `range`，争取 `ref`，能 `const` 更好；避免 `type=index` 当「用了索引就行」。
- 组合索引：区分度高的在左；等号条件列优先于范围列。
- 防止字段类型不一致导致**隐式转换**而使索引失效。

### 参考：建索引的误解

- 宁滥勿缺（一查询一索引）  
- 宁缺勿滥（怕拖慢写入就几乎不建）  
- 抵制唯一索引（只靠应用防重）

## 3. SQL 语句

### 必须

- 统计行数用 `count(*)`，不要用 `count(列名)` / `count(常量)` 冒充「行数」（`count(列)` 会忽略该列 NULL）。
- 注意 `count(distinct col1, col2)`：任一列全 NULL 时结果可能为 0。
- `sum(col)` 在全 NULL 时返回 NULL → 注意 NPE；应用层或 SQL 内做空保护。
- 判断 NULL 用 `IS NULL` / `IS NOT NULL`（或 `ISNULL()`），不要用 `= NULL` / `<> NULL`。
- 分页：`count` 为 0 则直接返回，勿再跑分页查询。
- **禁止外键与级联**；引用完整性在应用层保证。
- **禁止存储过程**（难调试、难扩展、难移植）。
- 数据订正：删改前先 `select` 确认，再执行更新。

### 推荐 / 参考

- `in` 能免则免；必须用则控制元素数量（建议 ≤ 1000）。
- 字符集：业务需要表情用 `utf8mb4`；注意 `LENGTH`（字节）与 `CHARACTER_LENGTH`（字符）差异。
- 开发代码中慎用 `TRUNCATE`（无事务、不触发 trigger，易事故）；日常删数用带条件的 `DELETE` 并先确认。

## 4. 查询与写入写法

### 必须

- 查询字段列表写清楚，**禁止 `SELECT *`**。
- SQL 参数必须绑定传参，**禁止拼接字符串**生成 SQL（注入风险）。
- 结果集以明确的列清单承载，不要用松散的键值结构当查询结果契约。
- 更新行时同步更新 `gmt_modified`（或项目等价修改时间字段）。
- 分页在数据库完成；禁止「查全表再在内存截取」的假分页。

### 推荐

- 只更新变更列，不要整行无差别覆盖写入。
- 大批量写入走批量语句，避免逐条往返；单批要有数量上限。
- 长事务会长期占用连接与锁资源：单条语句操作的数据量要有边界，不要在一条语句里改动超大范围的行。

## 5. 实例参数与运维

### 5.1 字符集与排序规则

- 默认 `utf8mb4`；需要存储表情符号时必须 `utf8mb4`（`utf8` 存不下 4 字节字符）。
- 排序规则全库统一（如 `utf8mb4_general_ci` / `utf8mb4_0900_ai_ci`），**跨表 join 字段的字符集与排序规则必须一致**，否则索引失效。
- 注意 `LENGTH`（字节）与 `CHARACTER_LENGTH`（字符）的差异。

### 5.2 连接与超时

| 参数 | 说明 |
|------|------|
| `max_connections` | 按实际并发设置，避免连接耗尽 |
| `wait_timeout` / `interactive_timeout` | 空闲连接回收时间；需大于连接池的空闲探活间隔 |
| `max_allowed_packet` | 单次传输包上限；大字段/批量插入需调大 |
| `lock_wait_timeout` | 锁等待超时，避免长时间挂起 |
| `innodb_lock_wait_timeout` | 行锁等待超时（默认 50s，可按业务下调） |

### 5.3 事务隔离级别

- 推荐 **READ-COMMITTED**：间隙锁范围小、并发度高；binlog 格式需为 `ROW`。
- 不要为「省事」把隔离级别降到 READ-UNCOMMITTED。

### 5.4 存储与缓冲

- `innodb_buffer_pool_size`：独占实例建议设为物理内存的 **50%~70%**。
- `innodb_flush_log_at_trx_commit` 与 `sync_binlog`：按数据安全与性能的权衡设定，主从/主备场景通常取双 1。

### 5.5 慢查询与观测

- 开启**慢查询日志**，设定合理阈值（`long_query_time`，如 1s），定期复盘 Top SQL。
- 上线/调优前后用 `explain` 对比执行计划，不要凭感觉判断索引是否生效。
- 建表与改表要有可追溯的变更脚本，结构与数据脚本分离。

## 6. 核对清单

- [ ] 表名/字段小写；单数表名；无保留字；有 id + 创建/修改时间  
- [ ] 是否字段 `is_xxx` + tinyint；金额/精确小数用 decimal  
- [ ] 唯一业务键有 uk；索引命名 pk_/uk_/idx_；varchar 索引有长度  
- [ ] 无外键级联、无存储过程；无左/全模糊搜主路径  
- [ ] count/sum/NULL 语义正确；深分页有策略  
- [ ] 无 `SELECT *`、无拼接 SQL；结果列清单明确；更新带 modified 时间  
- [ ] 字符集/排序规则统一；慢查询已开启；连接与超时参数按并发设置  

**打回语**

- 「禁止 float 存金额；改 decimal。」  
- 「业务唯一必须 uk，不能只靠先查后插。」  
- 「禁止三表以上 join；关联列类型一致且有索引。」  
- 「禁止拼接 SQL 与 SELECT *。」  
- 「禁止库级外键级联；完整性放应用层。」  
- 「join 字段字符集/排序规则不一致，索引会失效。」
