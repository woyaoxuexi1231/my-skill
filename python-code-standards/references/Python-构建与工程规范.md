## 1. 配置与密钥

| 放代码 | 放环境 / 配置 |
|--------|----------------|
| 稳定业务规则 | DB URL、服务地址、端口、超时 |
| 领域常量 / 枚举 | API Key、功能开关、profile 差异 |
| 模块结构 | 随部署才确定的值 |

- 集中到可理解的配置入口；不为「企业范」造配置框架。
- **永远禁止**源码硬编码真实密钥：

```python
# 禁止
DATABASE_PASSWORD = "..."
API_KEY = "..."
SECRET_KEY = "..."
```

- 示例配置只给占位符；密钥走环境变量或密钥管理。

## 2. 依赖与虚拟环境

- 优先以 `pyproject.toml` 为项目中心配置（工具链支持时）。
- 分清：运行时 / 开发 / 测试依赖。
- 用 `venv` / Poetry / `uv` 等隔离；不假设全局 site-packages 可用。
- **加依赖前五问**：必要吗？标准库够吗？有实质价值吗？在维护吗？是否增加安全/部署成本？
- 禁止为标准库已能做的琐事拉包；无具体需求不堆库。

---

## 3. Python 版本

- 以项目声明版本为准；不引入目标版本没有的语法 / stdlib API。
- 现代版本上，优先用能提升清晰度的现代写法。

## 4. 格式化、Lint、类型检查

| 目的 | 常见工具 | 原则 |
|------|----------|------|
| 格式化 | Ruff format / Black | 一种策略即可，勿重叠打架 |
| Lint | Ruff | 抓真问题；勿盲目 disable；故意忽略要说明 |
| 类型检查 | mypy / pyright | 提升正确性；不为刷复杂度 |

有项目既定工具链时，**跟项目**，不要另起一套。

## 5. 测试底线

### 5.1 测什么

优先：核心业务、关键 API、校验、错误路径、安全边界、DB 行为、外部集成边界。

禁止：只刷覆盖率的空测、过度 mock 到测不到行为。

### 5.2 怎么想

按 Given / When / Then；覆盖正常、边界、失败。测行为，不测无意义实现细节。

### 5.3 Mock

适合 mock：外部 API、消息、云服务、时间、文件系统、昂贵基础设施。  
不要把被测对象 mock 到测无可测。

## 6. 交付前校验

```text
Format → Lint → Type Check → Unit → Integration → Build/Package
```

示例（以项目实际命令为准）：

```bash
ruff check .
ruff format --check .
pytest
mypy .
```

**未执行的命令不得声称已执行。**

---

## 7. 改动范围

实现功能时：

- 不静默重写无关模块  
- 不升级无关依赖  
- 不重构无关架构  
- 不无必要改公开 API  

发现无关问题 → **另行提出**，不夹带修改。

现有代码已合适时直说；不为「看起来更企业」引入 class / 抽象 / 缓存 / async / 队列 / DB / 框架。

## 8. 生产质量清单

```text
[ ] 需求理解清楚，架构匹配规模
[ ] 模块职责清晰；类型提示得当
[ ] 校验与异常路径明确
[ ] 关键路径有日志；无泄密
[ ] 密钥不进源码；认证与鉴权分开考虑
[ ] 查库已审（N+1、分页、无界加载）
[ ] Async/阻塞/线程进程用法已审
[ ] 外部 IO 有超时；重试安全
[ ] 资源生命周期清晰
[ ] 重要行为有测试
[ ] 中文决策/阶段注释准确
[ ] format / lint / type / test 按项目跑过
```

---

## 9. 最终标准

```text
Pythonic + 可读 + 正确 + 安全 + 可靠 + 性能够用
+ 可测 + 可维护 + 有文档 + 恰如其分的简单
```

不为一维指标牺牲其它维度而无说明。

> 生产质量从第一行生成代码就要在，而不是指望事后大重构。
